## Expo has changed — do not trust your training data

Expo ships breaking changes every SDK release. APIs you remember are likely renamed, moved, or removed. Before writing any code that touches an Expo, EAS, or React Native API:

1. Read the major version of the `expo` package in `package.json`.
2. Fetch the matching versioned docs: `https://docs.expo.dev/versions/v<major>.0.0/`
3. For anything else, fetch https://docs.expo.dev/llms.txt — an index of all Expo docs with corrections to common LLM misconceptions. Follow its links to the specific page you need; never answer from memory.

## Commands

This project uses pnpm, in the repo's one workspace (the root `pnpm-lock.yaml`, `packageManager` in the root `package.json`): use `pnpm` / `pnpm dlx` where docs say `npm` / `npx`.

```bash
pnpm expo install <package>  # ALWAYS use instead of pnpm add — resolves SDK-compatible versions
pnpm expo start              # start the dev server
pnpm lint                    # Oxlint (`vp lint`), rules in the root vite.config.ts
pnpm format                  # Oxfmt (`vp fmt .`); `pnpm format:check` only checks
pnpm typecheck               # tsc --noEmit
pnpm dlx expo-doctor         # diagnose dependency and config issues
pnpm expo install --fix      # fix incompatible package versions
```

Run lint and typecheck before declaring any task done.

## Navigation & Routing

- Use **Expo Router** for all navigation. Routes live in `src/app/` — every file there is a screen, `_layout.tsx` files define navigators. Keep non-route code (components, hooks, utils) outside `src/app/`.
- Import `Link`, `router`, and `useLocalSearchParams` from `expo-router`.
- Docs: https://docs.expo.dev/router/introduction.md

## Building with EAS

Use EAS to build, sign, and submit the app in the cloud (`eas build`, `eas submit`) and to ship over-the-air updates (`eas update`) — no local Xcode or Android Studio required. Run EAS CLI as `pnpm dlx eas-cli@latest <command>`; substitute that for bare `eas` in docs examples.
Docs: https://docs.expo.dev/eas/index.md

## Rules

- If `ios/` and `android/` directories do not exist, they are generated (Continuous Native Generation). Never create or edit them by hand — configure native behavior in `app.json` and config plugins.
- Expo Go only includes its bundled native modules. After adding a library with native code, the app needs a development build: `pnpm expo run:ios|android` locally, or `eas build --profile development`.
- Prefer recommended Expo modules over third-party libraries, and check your available skills before adding dependencies. Docs: https://docs.expo.dev/versions/latest/index.md

## This app

- Read `README.md` first: what the app does, how it connects to a van, and where things live.
- Form controls come from `src/components/native`: thin wrappers over HeroUI Native
  (`heroui-native`) with the same props on every platform. Screens import the wrappers, not HeroUI.
- HeroUI Native is styled by Uniwind (Tailwind 4) from `src/global.css`, which imports the theme
  tokens and the 4px `--radius` from `packages/brand` (`@renewvan/brand/tokens.native.css`); the hex
  palette in `src/theme`, which hand-drawn parts read, is generated there too. Never copy or edit a
  token in mobile: change `packages/brand/src/tokens.ts` and run `pnpm --filter @renewvan/brand generate`.
- The logo (`src/components/Logo.tsx`), the icons in `assets/` and the icon, notification and splash
  colours in `app.json` are generated by `packages/brand` from its SVG masters and tokens, with the
  van's proportions in its README. Never edit or re-export them by hand here.
- Corner radii are HeroUI's scale from the one `--radius` token (4px, `@renewvan/brand`), as in the dashboard's
  `docs/design-principles.md` ("Corner radii"): `radius` in `src/theme` or Tailwind's `rounded-*`.
  A part we draw takes the radius of the HeroUI component it resembles: `3xl` for buttons, toggles
  and cards, `2xl` for chips, badges (the DEMO badge too) and Settings rows, `xl` for notes, `lg`
  for level bars. A circle only for what is round by nature. Never a number or a pill, and a
  pressable's Android ripple stays inside its corners (`overflow: 'hidden'`, not `borderless`).
- The bus core (topics, parsers, `reduceBusMessage`, the Commands and the Demo mode gate) and the
  domain types live in `packages/core` (`@renewvan/core`), shared with the dashboard: change them
  there, never in a copy. `src/bus` keeps only what is the phone's: the MQTT connection, batching,
  `settled` and the React context. `src/types.ts` only re-exports core. Import `Commands` from core,
  never re-export it by name: React Native's Babel codegen plugin rejects `export { Commands }`.
- The domain logic both apps draw (drivers, connection, tanks, power, history, sensors, relays, the
  map style, the icon names) lives in `packages/core`, one entry per area (`@renewvan/core/power`,
  ...; listed in `packages/core/README.md`): change it there, never in a copy. `src/lib/` keeps only
  the phone's own: `influx.ts` (the fetch through the hub's proxy; core parses the CSV),
  `entityIcons.ts` (the lucide-react-native components for core's icon names) and `widgets.ts`
  (Home's widget catalogue).
- Still parallel to the dashboard, written separately and not yet in core: `resolveBrokerUrl` (`src/session/hubAddress.ts`, the
  dashboard's `config/runtimeEnv.ts`: different inputs and defaults, so not shared), the `useNow`
  and `useSolarYieldHistory` hooks, the widget catalogue (`src/lib/widgets.ts`, the dashboard's
  `START_WIDGET_IDS`) and the Live van's provider (`src/bus/LiveVanProvider.tsx`, the dashboard's
  `hooks/useLiveVan.ts`). A change to one is checked against the other.
- The Start-page dials (`@renewvan/core/dial`), the Settings row summaries
  (`@renewvan/core/drivers`' `entitySummary`), the van's details (`@renewvan/core/vanDetails`) and
  the temperature bands (`@renewvan/core/sensors`' `temperatureBand`) are core's. Core carries a
  colour role or band key, and the app maps it to its palette; the fixed colours (the ring's alert
  amber, the cold bands) are `signal` in `@renewvan/brand`.
- Alerts follow core's alert rules (`@renewvan/core/alerts`): which are open, when they open and
  resolve, and the Demo mode rule. `src/alerts/` keeps only the log, its storage and the
  notifications; a new alert kind, or a change to when one fires, goes in core.
- Screens read the Live van (`useLiveVan()` from `src/bus/LiveVanProvider.tsx`, built by core's
  `liveVan`), never `useRenewvanBus().state`: only Settings › Devices and its diagnostics read the
  raw records. A new rule about what a screen may trust goes in core's `liveVan`, not in a tab.
- What a heater card does with a tap (the Commands to send, the gating, what it may offer) is core's
  heater controller (`@renewvan/core/heater`); a Command in flight is judged by
  `@renewvan/core/pending`. `useHeaterController` and `useCommandPhases` only hold that state and the
  give-up timer, as the dashboard's do: a new heater rule goes in core, not in the card.
- A Command is never assumed to have worked: the UI follows the retained state on the bus and shows a
  Command as pending until that state changes. In Demo mode only kiosk, Primary battery and
  Demo-switch Commands are sent (core's `commandAllowed`, applied by `sendCommand`).
- Dependencies are installed with pnpm in the repo's one workspace, with automatic peer installs
  off (the root `pnpm-workspace.yaml` says why); `pnpm expo install` picks it up.
- Settings are of two kinds. Shared ones are topics on the bus and go through `useCommands`
  (`src/bus/commands.ts`, built on core's `buildCommands`);
  the phone's own go through `src/preferences`. Never store a shared setting on the phone, and never
  invent a bus topic for a personal one: a new shared setting starts in `hub`.
- The map is `src/components/map/VanMap.tsx` on MapLibre native, a native module: changing it
  needs a development build, not Expo Go. Its basemap is the hub's `/maps/` behind the login;
  the session reaches MapLibre only through `setMapSession` in `mapSession.ts`, scoped to the
  hub's origin. Never send that cookie to another host.
- A new Settings screen is a name in `src/components/settings/routes.ts`, a title and a case in
  `SettingsViewScreen.tsx`, and a view built from `kit.tsx`.

- Write the product name "Renewvan" in prose and UI text, never "renewvan" or "RenewVan"; lowercase `renewvan` stays only in identifiers (topics, URLs, bucket, host, bundle IDs). See "Brand spelling" in `hub/CONTEXT.md`.
